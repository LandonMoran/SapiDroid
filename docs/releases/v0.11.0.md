# SapiDroid 0.11.0 — faster engines, a profiler, signed releases

This is the first release since 0.10.0. It is mostly about speed and about being
able to prove it: all four engine families got kernel work, the repository grew a
benchmark that compares every kernel against the original SapiDroid, and an
opt-in profiler now reports where a real request spends its milliseconds on the
device. Releases are signed by the workflow and install over earlier versions.

Nothing about the voices changed: same engines, same output. Every kernel below
was checked bit for bit against the previous build (the benchmark digests every
output and fails the report if a single bit moved).

Pick `app-arm64-v8a-release.apk` for virtually every current phone, or the
universal APK if you are unsure. Voice data is still not included; install it
from the app as before.

## Voices

- **George, Susan, Hazel, James and Catherine now speak the phone ids their
  models were trained on.** Microsoft shipped two English phone databases; the
  frontend always produces American ids, so every phoneme of the en-GB and en-AU
  voices was matched against the wrong acoustic model in 0.10.0 and came out
  unintelligible. The engine now works out which database a voice's own models
  use and translates the ids before asking them, so those voices speak, while
  the American, Canadian and Indian voices synthesize byte-identically to
  before. (Sarah and Matilda are fixed the same way but are still not offered:
  their model format is one the engine cannot load.)

## Engine speed

Kernel work across the four engines, all bit-identical. Each row is that
kernel's time in the new build against the original SapiDroid compiled the same
way; `bench/run.sh` rebuilds the whole table (43 kernels) from both trees.

| Kernel | vs original `-O2` (what 0.10.0 ran) | vs original at the same `-O3` flags |
| --- | --- | --- |
| SAPI 4 all-pole filter (per sample) | 1.94x | 1.95x |
| SAPI 4 pulse folding (per call) | 4.17x | 1.80x |
| SAPI 4 place + add halves | 5.28x | 1.30x |
| SAPI 4 inverse FFT (256 point) | 1.07x | 1.00x — flag only |
| SAPI 5 inverse FFT (256 point) | 1.29x | 1.09x |
| SAPI 5 LSF to LPC | 1.41x | 1.01x |
| Anna bit reader (per call) | 1.41x | 1.51x |
| Anna 16th-order FIR | 3.69x | 1.00x — flag only |
| Anna VQ add | 1.45x | 0.98x — flag only |
| Anna adaptive codebook vector | 1.32x | 1.03x |
| OneCore 41-tap FIR | 2.74x | 2.82x |
| OneCore fixed-point vocoder | 1.23x | 1.12x |
| OneCore Sonic rate change | 2.79x | 0.99x — flag only |

The second column matters: several of the largest ratios are the shipping flags
moving from `-O2` to `-O3 -fno-math-errno` on unchanged source, not a rewrite.
`-ffp-contract=off` and `-fno-fast-math` stay on, so no floating point
operation is reassociated or fused and the engines remain bit-exact.

New in this release, measured on its own with alternating A/B runs (these two
kernels are small enough that their share of the end-to-end figure disappears
into the benchmark's noise):

| Kernel | Before | After | |
| --- | --- | --- | --- |
| OneCore integer MLPG band window (Zira, Mark; per dimension-frame) | 62.7 ns | 55.4 ns | 1.13x |
| OneCore Sonic AMDF period search (David; per search) | 24.7 us | 18.9 us | 1.31x |

- The MLPG pass converts the model's Q4 window coefficients once per chunk
  instead of once per inner iteration, and hoists the precision-times-window
  product out of the tap loop. It runs for every output dimension of every LSF
  chunk, so it is the largest single piece of arithmetic on the Zira and Mark
  path.
- The Sonic AMDF sums four accumulators instead of one. The sum is of unsigned
  16-bit differences, so it cannot overflow and the grouping is exact.
- One edit was measured and dropped: byte-sized pulse marks in the float
  excitation were 0.82x, so the int array stays.

## Profiler

`./gradlew :app:assembleDebug -Pprofile` (or the `sapidroid-profile-apk` CI
artifact) builds a variant that times voice loading, the engine call, the first
PCM block, the JNI copy and the audio queue, and prints one ranked table per
request. The app's **Export profile log** button shares the file; `adb pull
/sdcard/Android/data/org.sapidroid.tts/files/profile/profiling.txt` works too.
Release builds compile every instrumentation site out.

CI can collect those tables without a phone: the `profile-on-emulator` job
boots an API 34 emulator, lets the app fetch Microsoft's voice data through its
own download buttons, speaks a few sentences, exports the tables and uploads
them together with the logcat, and a follow-up job prints the ranked totals at
the top of a clean log (see **Measured on an emulator** below).

## Releases

- `.github/workflows/release.yml` builds the APKs from a version tag, signed
  with the keystore in the repository secrets, sets the version from the tag,
  verifies every APK's signing certificate against `EXPECTED_CERT_SHA256` (so a
  wrong keystore cannot ship an update that forces users to uninstall, which
  would delete their voice data) and attaches one APK per ABI plus a universal
  one to the release.
- A tag's notes can live in `docs/releases/<tag>.md`, which the workflow copies
  into the release body; GitHub's generated commit list is appended after it.

## Measured on an emulator

The `profile-on-emulator` job ran against this build (API 34 x86_64 AVD, MSVC's
voice data fetched by the app itself, the same sentence six times: David three
times, SAPI 5 Sam three times). Milliseconds per request, engine rows as the
engine process reports them:

| Voice | `speak:call` | `speak:first_pcm` | `audio:queue_push` | `jni:pcm_copy` |
| --- | --- | --- | --- | --- |
| David (OneCore, float vocoder + Sonic) | 7.1 / 9.2 / 7.9 ms | 6.7 / 8.6 / 7.6 ms | 0.29 / 0.43 / 0.24 ms | 0.11 / 0.16 / 0.08 ms |
| Sam (SAPI 5) | 14.4 / 16.4 / 14.7 ms | 0.61 / 0.57 / 0.56 ms | 1.72 / 0.46 / 1.34 ms | 0.21 / 1.06 / 0.18 ms |

What that says: on David the engine spends almost all of its 7-9 ms before the
first sample (the frontend and the first vocoder block), which is the number to
attack next; on Sam the first sample arrives after 0.6 ms and the rest of the
call is the engine producing audio. The JNI copy is negligible on both (0.18 MB
and 0.25 MB per request). `audio:deliver` dominates every table at ~5 s per
request, but that is the platform draining the audio in real time, not engine
time — it is why the report ranks it first and why it must be read separately.

These are emulator numbers under KVM on a server CPU: the DSP runs far faster
than on a phone, so only the shape of each request transfers, not the absolute
milliseconds.
